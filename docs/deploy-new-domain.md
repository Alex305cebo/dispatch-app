# Перенос приложения на новый домен и новый хостинг

Как поставить это приложение на чужой домен (или целиком на чужой хостинг), когда
продаём его как готовое решение.

Всё ниже, кроме раздела «Путь Б», **проверено вживую 28.07.2026** — так подняли
`app.mayalogisticsinc.com` поверх работающего `dispatch4you.pro`.

---

## Главное: в коде домена нет

Это выяснено проверкой, а не на глаз — и это причина, почему перенос дешёвый:

| Что обычно ломается при смене домена | Как здесь |
|---|---|
| Абсолютные URL в коде | Нет ни одного. Все ссылки относительные. |
| Кука сессии | `dispatch_session`, `path:'/'`, **без атрибута `domain`** (`app/demo/route.ts`) → привязана к хосту автоматически, на любом домене работает сама. |
| Редиректы после логина | `middleware.ts` делает `rewrite` на `/login` — относительный путь, домен не участвует. |
| Базовый URL в конфиге | `NEXT_PUBLIC_APP_URL` объявлен в `.env.local.example`, но **не читается ни одной строкой кода**. Менять его при переносе не нужно. ⚠️ Комментарий рядом с ним («адрес, на который указывает QR расширения») устарел — если будешь возвращать эту логику, помни, что сейчас она мёртвая. |
| Хардкод домена | Только `demo@dispatch4you.pro` — это **email демо-аккаунта** (`lib/demo.ts`, `lib/schema.sql`), логин, а не адрес сайта. На работу на другом домене не влияет. |

**Вывод:** менять код ради нового домена не нужно. Перенос — это DNS + панель хостинга.

## Путь А — новый домен на том же приложении

Когда: свой второй домен, домен клиента, которому продали доступ к общей установке.
Время: ~5 минут + до часа на DNS.

Требование: домен уже зарегистрирован и **его NS указывают на Hostinger**
(`ns1/ns2.dns-parking.com` и т.п.). Если NS чужие — сначала переводим их, иначе
парковка не пройдёт.

1. hPanel → **Websites** → нужный сайт → **Domains** → **Parked Domains**.
2. Ввести полное имя (`app.example.com` или `example.com`) → **Park**.
3. Дождаться статуса **Connected** в таблице. DNS-запись создаётся автоматически —
   руками в зоне ничего добавлять не надо.
4. hPanel → **Security** → **SSL certificate**: там должна появиться строка нового
   домена, `Lifetime SSL`, `Active`. Выпускается сам, обычно за минуты.
5. Проверить: `https://<новый-домен>/login` отдаёт 200, `/demo` отдаёт 307.

### Что при этом НЕ ломается (проверено)

Парковка поддомена не трогает остальную зону. После парковки
`app.mayalogisticsinc.com` перепроверено:

- A-записи апекса остались на GitHub Pages (`185.199.108-111.153`) — сайт-визитка жив;
- `MX` остался на `...mail.protection.outlook.com` — корпоративная почта жива;
- основной домен приложения (`dispatch4you.pro`) продолжал отвечать 200 всё время.

Тем не менее **после каждой парковки прогоняй эту проверку** — одна команда:

```bash
dig +short example.com A; dig +short example.com MX; dig +short app.example.com A
```

### Откат

hPanel → Parked Domains → корзина напротив домена. Основной домен не затрагивается.

## Путь Б — отдельная установка для клиента

Когда: клиент хочет своё, на своём хостинге, со своей базой. **Этот путь целиком
пока не проходили — шаги ниже выведены из того, как устроена текущая установка.**

Текущая боевая конфигурация, которую воспроизводим (hPanel → Dashboard):

- тип: Hostinger **Web App**, план Business;
- источник: **GitHub**, репозиторий `dispatch-app`, ветка `main`, root `./`;
- авто-деплой: включён (пуш в `main` → сборка);
- Framework: Next.js, Node **22.x**, build/output — Default;
- SSL и CDN — включены.

Порядок:

1. **Репозиторий.** Клиенту — свой форк/копия, иначе его пуши поедут в твой прод.
2. **Хостинг.** Новый Web App, подключить к его репозиторию, Node 22.x.
3. **База.** Своя Neon-база. Схема — `lib/schema.sql`, накатывается `scripts/db-init.mjs`.
4. **Переменные окружения** (hPanel → *Environment variables*, они per-website):
   - `DATABASE_URL` — обязательно, своя;
   - `ELD_USERNAME` / `ELD_PASSWORD` / `ELD_COMPANY_ID` — креды **их** ELD-аккаунта;
     без всех трёх поллер просто молчит, приложение работает;
   - `CRON_SECRET` — закрывает `/api/eld-poll` и `/api/tg-poll`; без него оба
     эндпоинта отдают отказ, то есть внешний пингер работать не будет.
5. **Домен** — дальше как в Пути А.
6. **Бэкапы** — `.github/workflows/backup.yml` работает от `DATABASE_URL`; в новом
   репозитории нужен свой секрет.

### ⚠️ Блокер, который надо решить до первой продажи

Сейчас **одна установка = один парк траков**: ELD-креды берутся из `process.env`,
а таблица `settings` глобальная (не разделена по компаниям). То есть посадить
второго клиента в ту же установку нельзя — он увидит чужой ELD.

Пока это так, у продажи есть ровно два честных варианта:

- **отдельная установка на клиента** (Путь Б) — работает уже сегодня;
- **общая установка** — только после задач **P0** (настройки per-company) и
  **P3** (интеграции per-company) из [`saas-tiers-plan.md`](saas-tiers-plan.md),
  и обязательно после **P4** (аудит изоляции по `company_id`).

Не продавать место в общей установке, пока P0/P3/P4 не закрыты.

## Чек-лист «перенос закончен»

- [ ] `https://<домен>/login` → 200
- [ ] `https://<домен>/demo` → 307, демо открывается без регистрации
- [ ] `https://<домен>/track/<id>` → карта трака, без логина
- [ ] вход реальным пользователем работает, сессия держится после перезагрузки
- [ ] старый домен (если оставляем) продолжает работать
- [ ] апекс и `MX` домена не изменились
- [ ] SSL `Active`, http автоматически уходит на https
