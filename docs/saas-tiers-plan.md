# SaaS: тарифы, триал и хранилище — план внедрения

Как превратить приложение в продукт для нескольких компаний. Порядок задач — по
зависимостям: каждая следующая опирается на предыдущую.

Хорошая новость: фундамент уже есть — все данные (грузы, траки, документы,
пользователи) разделены по `company_id` через `companyScope()`. Достраиваем
поверх, ничего не переписываем.

---

## Тарифы (что продаём)

Оба массовых тарифа — **один код, одна установка**. Разница только в галочках у
компании, приложение НЕ форкается.

| | Тариф 1 «Под ключ» (дороже) | Тариф 2 «Self-service» (дешевле) |
|---|---|---|
| Где крутится | Твой хостинг/БД | Тот же общий SaaS |
| Файлы | В твоём облаке (входит) | Их Cloudflare R2 (их аккаунт, их счёт) |
| Кто администрирует | Ты: мониторинг, ошибки, доработки | Они сами: юзеры, настройки, свой бакет |
| Выделенный админ | Да | Нет, стандартная поддержка |
| Обновления | Автоматически | Автоматически (тот же код) |
| Кастомизация | Индивидуально | Как у всех |

**Enterprise / on-prem** — отдельный трек, только под запрос: своя коробка, ты не
имеешь доступа, обновления «выпустил → они накатили» (не автоматом). Не часть
массовой сборки, делаем только когда придёт клиент, готовый за это платить.

## Триал

- Демо (`/demo`) уже есть — «витрина», парадная дверь без регистрации.
- Триал 14 дней — своя компания, свои реальные данные. Это то, что конвертирует.
- Оплату НЕ автоматизируем на старте: истёк триал → клиент пишет → продлеваешь
  руками. Stripe — потом, когда поток оправдает возню.

## Порядок задач

### P0. Настройки per-company `[фундамент, делать первым]`
Сейчас таблица `settings` глобальная (`getSetting(key)`). Триал, тариф, ключи R2,
ELD-креды — всё должно быть по компаниям.

- `settings`: составной ключ `(company_id, key)`; миграция существующих строк на
  `company_id='default'`.
- `getSetting/getSettings/setSetting` — брать `companyId` (из `companyScope()`).
- Проверить всех, кто читает настройки, что они получают компанию из сессии.

Размер: средний. Ломает мало, но трогает точечно во многих местах.

### P1. Тариф компании + триал
Опирается на: ничего (можно параллельно с P0, но использует поля компании).

- `companies`: `plan TEXT DEFAULT 'trial'` (`trial|self|managed`),
  `trial_ends_at TIMESTAMPTZ`.
- При заведении компании: `trial_ends_at = now() + 14 days`.
- Плашка «осталось N дней» (компонент, читает `trial_ends_at`).
- Мягкая блокировка после истечения: только чтение + баннер «продлить». Гейт в
  write-экшенах: `assertActive(company)` (триал не истёк ИЛИ план платный).
  Данные не трогаем.
- Продление — вручную (ты бампаешь `trial_ends_at`). Позже — Stripe.

Размер: малый-средний.

### P2. Storage-адаптер + свой Cloudflare R2 `[фича тарифа 2 + твоя экономия места]`
Опирается на: P0 (ключи хранятся в per-company настройках).

- `lib/storage.ts`: `putDoc(companyId, bytes, mime) -> ref` и
  `getDoc(ref) -> bytes`. Один адаптер, две реализации:
  - нет ключей у компании → пишем BYTEA в Neon, как сейчас (дефолт);
  - есть ключи → пишем в R2 компании (S3-совместимо; `aws4fetch` — крохотный, без
    тяжёлого SDK).
- `documents`: добавить `storage_ref TEXT` (bucket+key); `data BYTEA` сделать
  nullable (для R2-пути данные не в БД).
- **Secret Access Key**: шифруем в БД (env-ключ шифрования), клиенту наружу не
  отдаём — в поле маска `••••`. Не гонять через URL.
- Секция «Хранилище файлов» в админке (мокап уже согласован): выбор
  «наше облако / свой R2» + 4 поля + «Проверить подключение» (пишем и читаем
  тестовый объект, показываем результат).
- Меняются только 2 точки доступа к файлам: запись `uploadDocument`, чтение
  `/view/[id]` и `/api/docs/[id]`.

Размер: средний. Изолировано за адаптером.

### P3. Интеграции per-company `[нужно до первого чужого клиента со своим парком]`
Опирается на: P0.

- ELD/GPS (`ELD_USERNAME/PASSWORD/COMPANY_ID`) — из `process.env` в настройки
  компании. Без этого все клиенты сидят на ТВОЁМ ELD-парке — продавать нельзя.
- Реквизиты компании / инвойс — уже per-company (`getCompany`), проверить.
- Telegram — per-company, если используется.
- Gemini-ключ — можно оставить общим (твой ключ, твой расход). Пометить в коде.

Размер: средний (в основном ELD).

### P4. Аудит изоляции `[ГЕЙТ: до первого реального платящего клиента]`
Опирается на: ничего, но критично перед хранением чужих данных.

- Пройтись по всем запросам: каждый ли scoped по `company_id`/`companyScope()`.
- Грепнуть сырые SQL без скоупа. Утечка здесь = один клиент видит грузы другого.
- Точечный, но обязательный проход. Дёшево, критично.

Размер: малый (проверка), но блокирует go-live.

### P5. Онбординг новой компании
Опирается на: P0, P1.

- Завести компанию + первого админа + выставить триал.
- На старте — вручную (ты создаёшь). Self-serve регистрация — когда пойдёт поток.

Размер: малый (ручной), позже — форма регистрации.

### P6. Биллинг `[позже, когда поток оправдает]`
- Stripe, автосписание, привязка `plan` к подписке.
- YAGNI до тех пор, пока ручное продление не станет больно.

## Что делать в каком порядке (сжато)

1. **P0** настройки per-company — фундамент.
2. **P1** тариф + триал — можно запускать пилоты.
3. **P2** storage-адаптер + R2 — дифференциатор тарифов и экономия твоего места.
4. **P3** ELD per-company — до первого клиента со своими траками.
5. **P4** аудит изоляции — гейт перед реальными платящими.
6. **P5** онбординг (сначала руками).
7. **P6** биллинг — потом.

Enterprise/on-prem — отдельно, только под конкретный запрос.
